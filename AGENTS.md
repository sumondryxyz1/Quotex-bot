# AGENTS.md

## What this repo does

`market_qx_candles.py` streams **live candle data** from `market-qx.info`
(a Quotex / QxBroker white-label site) by talking directly to its trading feed.

## Key findings (hard-won, do not rediscover)

- `market-qx.info` is behind **Cloudflare managed challenge** and is
  **geo-blocked** ("Quotex is currently not available in your region") for this
  environment's IP. Plain `curl` and headless Chromium both fail; only a
  **headful** Chromium under `xvfb-run` (with `navigator.webdriver` masked) gets
  past the challenge.
- The website is irrelevant for data anyway: the trading terminal uses a plain
  **Socket.IO / Engine.IO v3** endpoint that serves public market data with no
  login:
  - `wss://ws2.market-qx.info/socket.io/?EIO=3&transport=websocket`
    (also `ws.market-qx.info`; `ws2` is the live one)
- Required handshake: read `0{"sid":...}` then `40`, then send
  `42["instruments/follow","<ASSET>"]` to receive live ticks. Send
  `42["tick"]` periodically as a keep-alive.
- Frame formats:
  - Live ticks (headerless binary frame `\x04[...]`):
    `[[ "<ASSET>", <epoch_seconds_float>, <price>, <dir:int> ], ...]`
  - Instrument list: `451-["instruments/list",{"_placeholder":true,"num":0}]`
    followed by `\x04[[id, symbol, name, type, ...], ...]` (arrives late,
    sometimes ~45s, or after an `instruments/list` request).
  - Live sentiment / depth: `451-["depth/change",...]` + `\x04[["<ASSET>",<int>]]`
- **Server-side OHLC history is NOT public.** `42["history/load",{...}]` and
  `451-["history/list/v2",...]` return nothing without an authenticated SSID
  (from `window.settings.token` on a logged-in trade page). Candle rows, when
  authenticated, are `[time, open, close, high, low]`.
- Sending `42["instruments/list"]` can drop the connection — prefer the `tick`
  keep-alive. Sending an empty/invalid `42["authorization",...]` also drops it.
- Because history needs auth, the script builds candles client-side by
  aggregating the live tick stream (`CandleBuilder`).

## Is the data really from Quotex? (verified 2026-11-07)

Yes — the WebSocket is Quotex's own feed (this site is a Quotex white-label):

- Host `ws2.market-qx.info` is Cloudflare-fronted with a valid TLS cert
  `CN=market-qx.info` (Google Trust Services).
- Server timestamps in each tick match the local clock to within ~0.3s, so the
  frames are produced live (not replayed).
- Prices move tick-by-tick (21-36 distinct values per 30s).

**But be precise about which data:**

- `_otc` symbols (e.g. `EURUSD_otc`) are **Quotex's own over-the-counter
  quotes**, generated by the broker. They stream 24/7 and are **not** the real
  interbank market. Verified: on Saturday (real FX closed) `EURUSD_otc` still
  moved 21 distinct prices in 30s.
- non-`_otc` symbols (e.g. `EURUSD`, `XAUUSD`) mirror the **real market** and
  freeze when it is closed — same test showed `EURUSD`/`XAUUSD` with 1 distinct
  price (frozen) while `EURUSD_otc` was live. These carry a small basis
  (e.g. EURUSD_otc traded ~0.0023 below EURUSD).

So: real broker feed, real-time, but OTC prices are broker-synthetic. Run
`python verify_feed.py` to reproduce this yourself.

## AI up/down bot

```bash
pip install -r requirements.txt
python make_synthetic.py                    # or record real data:
python collect_data.py EURUSD_otc 60 --hours 6
python train_model.py data/EURUSD_otc_60.csv --model out/model.pkl
python ai_bot.py out/model.pkl EURUSD_otc 60 --min-confidence 0.55
```

The model is a `GradientBoostingClassifier` on 26 features (returns, candle
geometry, EMA distances/slopes, RSI, MACD, Bollinger position/width, ATR%,
Stochastic, consecutive candles, hour-of-day). Label = did the *next* candle
close higher.

**Honest results — read this before trusting any number:**

- Random-walk synthetic data: edge ~0 (walk-forward acc ~50%, AUC ~0.51). The
  trainer correctly reports "no better than guessing".
- Momentum synthetic data: acc ~73%, AUC ~0.82 — the pipeline *can* learn when
  a real pattern exists.
- Live real EURUSD_otc with the *synthetic* model: ~30% hit-rate. Expected: a
  model trained on fake data knows nothing about the real feed.

To get a model that might work you must `collect_data.py` for a long time
(hours to days) and judge it ONLY by `train_model.py`'s walk-forward edge, never
by a short live run. If the edge is ~0, the honest answer is that there is no
predictable signal.

The flow is: **pick a pair → pick a timeframe → press Analyze**. The bot then
computes the indicator set on the candles for that exact (pair, timeframe) and

**Important UX fact:** the feed exposes *no* public OHLC history (verified — the
`history/*` events need an authenticated SSID). Candles are therefore built from
the live tick stream, so a timeframe needs `52 x period` seconds of uptime
before the first signal: ~4 min on 5s, ~52 min on 1m. The UI shows a progress bar
and ETA, and auto-fires the analysis once enough candles exist. History
accumulates in SQLite across restarts, so leave it running.

## Telegram signal alerts

`alerts.py` watches the candle store, runs the same rule engine as the dashboard,
and pushes a Telegram message on every *new* CALL/PUT signal. Alerts only — it
never trades.

```bash
./run_alerts.sh --whoami --token <TOKEN>   # one-time: find your chat id
./run_alerts.sh --test                     # verify the connection
./run_alerts.sh                            # watch 5s+15s
./run_alerts.sh --periods 5,15,60 --min-score 6
python alerts.py --dry-run --once          # preview, no credentials needed
```

Credentials come from `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`, `--token` /
`--chat`, or `telegram.json` (`{"bot_token": "...", "chat_id": "..."}`;
git-ignored). Setup: @BotFather -> `/newbot` -> token; message the bot once,
then `--whoami` prints the chat id.

Duplicate suppression: `data/alert_state.json` remembers the last action per
(pair, timeframe), so a signal only re-fires after it flips or the `--cooldown`
(default 300s) elapses. Uses only the standard library — no new dependency.

## Scanning all pairs at once

`scan.py` runs the engine over **every stored pair**, not one at a time. The
single `scan_all(store, periods, engine, ...)` function is the shared entry
point — the CLI, the dashboard's "Scan all pairs" button (`/api/scan`), and the
Telegram alerts all call it, so they can never disagree.

```bash
python scan.py                    # 5s, all pairs
python scan.py 5,15,60            # several timeframes
python scan.py --all-tf           # every timeframe that has data
python scan.py --all-tf --engine smart --top 30
python scan.py --all-tf --json    # machine-readable
python scan.py 5 --watch          # re-scan every 30s
```

A full pass over 91 pairs x 8 timeframes (728 series) takes ~0.6 s, so it runs
inline in the HTTP handler — no caching needed. Series with too few candles are
counted as `waiting`, not dropped silently. In the dashboard the **Scan all
pairs** card sits directly under *Select market*; it runs automatically on page
load and refreshes every ~20 s, so signals are visible without pressing
anything. Pick the scope (5s / 15s / 1m / 5s+15s+1m / all) and press **Scan
now** to force a pass. Responses send `Cache-Control: no-store` so a reload
always shows the current build.

Telegram uses the same path: `./run_alerts.sh --periods all --engine smart`
watches every pair x timeframe, with `--min-conf` (smart) or `--min-score`
(rule) as the floor and the usual per-series cooldown.

## Entry and expiry time

A signal is read from candles that have **already closed**, so the earliest
honest moment to act is the open of the next candle — never the price the
signal was derived from. `scan.entry_plan()` turns that into concrete times and
every row carries them:

| field | meaning |
| --- | --- |
| `entry_at` | clock time to enter — the next candle boundary at or after now |
| `expiry_at` | when the trade settles (entry + `expiry_candles` candles) |
| `entry_in` / `expires_in` | seconds from now, for a live countdown |
| `expiry_candles` | how many candles the trade runs (default 1) |

Entry is snapped to a real candle boundary and is **never in the past**; if the
scan lags, it moves forward to the next live boundary rather than quoting a
stale price. Set the horizon with `--expiry N` on `scan.py` / `alerts.py`, or
`&expiry=N` on `/api/analyze`. The dashboard shows the clock times plus a
per-second countdown in both the scan list and the Signal card. This is
presentation only — nothing is traded.

## Honest evaluation: signals have no measured edge

Three independent tools now agree that this feed is not tradable with candle
indicators. Read this before adding any more indicators.

### 1. `research.py` — 49 hypotheses, proper train/val/test

Precomputes each pair's features once, then tests 49 hypotheses (streaks, RSI
extremes, range fade, Bollinger, MACD/Stoch crosses, breakouts, hour-of-day,
always-CALL/PUT) with a time split and a Bonferroni bar on the held-out test set.

Result across 5s/15s/30s/1m/2m: **0 hypotheses survived out-of-sample.** At 1m,
2 cleared validation (body_reversal 55.1%, rsi_extreme_30_70 54.5%) and both
collapsed on test (50.4%, 53.5%). At 2m, 6 cleared validation and all 6 failed
test. This is textbook overfitting — the validation "wins" were noise.

### 2. `randomwalk.py` — the returns are a random walk
Per-pair normalised returns, pooled over 62 pairs (128k returns at 5s):

- autocorrelation at lags 1–10: all |z| < 2 (≈ 0)
- variance ratio: 0.997 / 0.991 / 0.997 at q = 2/5/10 (a random walk is 1.0)
- direction base rate: up 47.1% / down 46.9% / flat 6.1%

There is no linear structure to exploit. Note: pooling raw (un-normalised)
returns across pairs *fakes* significance because pairs have wildly different
price scales — always normalise per pair first.

### 3. Cross-pair lead-lag — nothing

Correlating one pair's move against another's next move: 0 of 30 ordered pairs
had |z| > 3 (expected ~0.3% by chance; top was z = −2.07, i.e. noise).

### 4. `edge.py` — no pair beats the payout

0 of 62 pairs had a hit-rate CI lower bound above the 85%-payout breakeven of
54.1%. Most sat at 40–48%, i.e. at or below a coin flip. `backtest.py --compare`
agrees: rule 47.5% (p=0.44), smart 53.4% (p=0.27), random control 46.7%.

### 5. Expiry horizon — also nothing (2026-11-07)

`research.py --horizon H` sweeps the expiry in candles. At 5s, horizons 1/2/3/5
all behaved the same: one hypothesis (`rsi_extreme_20_80`) cleared validation
(55.1%, 52.5%, 55.0%, 58.8%) and every time collapsed on the held-out test
(48.0%, 46.6%). Longer expiries do not reveal hidden drift — the edge is not
there at any horizon tested.

Both `research.py` and `edge.py` now filter by `--kind {all,otc,real}` and drop
dead pairs (`--max-flat`). Note the real (non-OTC) pairs are completely frozen
while the market is closed — flat rate 1.00 — so any test on them is meaningless
until market hours. Only the `_otc` (synthetic, always-on) pairs move 24/7.

### 6. Fewer wrong signals? Selectivity does not help (2026-11-07)

`selective.py` sweeps every knob that makes the rule engine *quieter* — threshold
2→8, trend-regime agreement, an ATR volatility gate (skip the flattest half), and
multi-timeframe confluence (5s signal must agree with the 1m EMA trend) — and
reports precision on the held-out last 40%.

Result: **nothing lowers the wrong-signal rate.** Raising the threshold only
shrinks the sample; the hit-rate stays ~50–53% and the CI always straddles the
54.1% breakeven. Adding the regime, volatility, or MTF filter makes it *slightly
worse* (52.9% → 52.2% with MTF, → 51.2% with the vol gate). Being pickier does
not find a better subset — it just fires less.

    python selective.py --period 60 --kind otc          # full sweep
    python selective.py --period 5 --limit 20 --mtf 60  # MTF confluence test

Practical takeaway: the only honest way to cut wrong signals on this feed is to
fire *less often*, not to fire *better* — and even that does not change the odds
per signal. Do not sell a "high-confidence" filter as an accuracy win.

### What this means

A binary option breaks even at `1/(1+payout)` — 54.1% at 85% payout. The feed
delivers ~50% and no rule tested moves that. Confidence is not calibrated either
(the 0.7–0.8 bucket hit 50%). The signals are presentation, not an edge.

The remaining honest avenues, none of which candle indicators can reach:

- **Non-OTC pairs during real market hours** — genuine FX microstructure exists,
  but it is weak and heavily arbitraged; OTC (what most of this data is) is
  synthetic and deliberately unpredictable.
- **Far more data on long timeframes** (days/weeks at 5m+), then re-run
  `research.py`. Three hours is nowhere near enough.
- **Exogenous data** (news, order flow, sentiment) — outside this feed entirely.

## Live signal journal (`journal.py`)

Records every signal the engines fire, then settles each one against the close
of its expiry candle and reports a win-rate with a Wilson CI against the payout
breakeven. This is the *forward* test — the backtest tools look at the past, the
journal measures what actually happens from now on.

    python journal.py --once                 # log current signals, settle done ones
    python journal.py --watch                # loop forever (every 30s)
    python journal.py --report               # show the track record
    python journal.py --report --engine smart

The dashboard runs the same loop in the background (`Hub._journal_loop`) and
exposes it at `GET /api/journal`; the UI shows a "Track record" card.

Settlement detail: a signal on (asset, period) at candle T enters at the next
boundary and expires `expiry_candles` later. Win/loss is the close of the expiry
candle vs the entry close — exactly what a binary option pays on. An unchanged
price settles `flat` (a tie, not a loss); these are almost all non-OTC pairs
while the real market is closed. `data/journal.db` is separate from the candle
store, so it survives independently.

## Demo → real money gate (`golive.py`)

The honest answer to "when can I use real money?" is: when the demo signals show
a *measured* edge, not before. `golive.py` runs a paper account through every
settled journal signal and checks hard criteria. It never connects to the broker
and never places a trade — no money is at risk.

Stages: `DEMO` (not enough data) → `NOT READY` (no edge) → `PAPER PASS` (edge
shows, keep testing) → `LIVE-READY` (all gates passed; a *small* real stake is
defensible). The dashboard shows this as the "Demo → Real money gate" card and at
`GET /api/golive`.

    python golive.py --report            # the verdict + paper equity
    python golive.py --simulate          # just the paper curve
    python golive.py --report --json

The gate requires ALL of: ≥300 settled decisive signals, hit-rate CI lower bound
above breakeven + 1%, p < 0.01, positive paper return, max drawdown ≤ 25%,
consistency across ≥5 pairs, and no single pair carrying >50% of trades.

At the time of writing the gate reads **DEMO/NOT READY** — exactly as it should.
Do not bypass it; if the edge ever appears, the gate is what proves it.

## Two engines: rule vs smart

`signal_bot.SignalEngine` (rule) counts indicator votes and fires at a fixed
threshold. `smart_engine.SmartEngine` is regime-aware:

- **ADX regime gate** — ADX<20 is a range (only mean-reversion plays), ADX>25 is
  a trend (only breakout/momentum plays), in between it stands aside. This is
  the core idea: mean-reversion rules lose in trends and momentum rules lose in
  chop, so the same rule set cannot work in both.
- **Volatility gate** — current ATR must be 0.5x–3.0x its recent *median*.
  (A percentile gate was tried first and rejected clean trends; see
  `test_smart_engine.py`.) Too calm = spread eats the move; too wild = news spike.
- **Breakout + higher-timeframe confirmation** — in a trend, price must clear
  the recent extreme and agree with the EMA(trend) direction.
- **Confidence 0..1** instead of a raw vote count, so callers can set a floor.

Both engines return the same `analysis.Analysis` shape, so the dashboard, the
scanner, and the alerts can switch with `--engine rule|smart` or the Engine
dropdown. `analyze_smart()` in `analysis.py` is the adapter.

### Honest backtest (do not skip this)

`backtest.py` walks stored candles forward and scores the *next* candle's
direction. It reports hit-rate with a 95% Wilson interval and a binomial
p-value, and can add a random control (`--control`) — the null you must beat.

```bash
python backtest.py --period 5 --compare --control
```

Measured on ~40 min of live 5s data (2026-11): rule 52.2% (p=0.19),
smart 53.2% (p=0.07), random control 49.2%. **Neither engine shows a
statistically significant edge yet.** More history is required before any
claim can be made. Treat every signal as an alert, never as a trade.

Do **not** tune `min_confidence` or the gates on this little data: a sweep gave
53.7% at 0.60–0.65 (p=0.04) but 51.0% at 0.70, and the buckets shift when the
debounce changes which candles fire. That instability is the signature of noise,
not edge. Re-run the backtest after collecting days, not minutes, of candles.

## Signal strategy

`SignalEngine` votes on each **closed** candle (weighted confluence):

- EMA(fast) vs EMA(slow) and price vs EMA(trend) -> trend direction
- fresh EMA cross / MACD cross -> momentum shift (strongest votes)
- RSI oversold/overbought, Stochastic cross, Bollinger-band breaks -> extras

Net score >= `--threshold` fires CALL (bullish) or PUT (bearish). Signals are
debounced so the same direction is not repeated back-to-back. Alerts only —
the bot does **not** place trades.

Live-verified: emits e.g. `🔴 PUT EURUSD_otc @ 1.11275` (score 4) on a real
downtrend from the market-qx feed.
